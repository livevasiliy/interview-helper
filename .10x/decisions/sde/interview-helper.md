### T7 — Microphone capture (code complete, NOT yet verified on a real mic)
- `MicrophoneCapture` (App/Audio): `AudioSource` over AVAudioEngine; checks mic authorization first (`AudioCaptureError.microphonePermissionDenied`), rejects a zero-rate/zero-channel input (`noInputDevice`), taps at the input's native format and converts with the shared `PCMConverter`. Rebuilds the tap on `AVAudioEngineConfigurationChange` (headphones plugged in, device switched) via a serial queue; calls `onUnexpectedStop` if it cannot recover.
- `AudioProbe` generalized to any `AudioSource`; new menu item **"Debug: Test Microphone (5 s)"** (WAV at `$TMPDIR/interview-helper-microphone.wav`). `AudioCaptureError` gained the two mic cases.
- No new Core logic, so no new unit tests; the conversion path is covered by T8 tests. Device-change recovery is untested (needs hardware).
- Known product caveat: without headphones the mic also picks up the interviewer from the speakers (echo). The two streams are separate, so QuestionDetector only reads the system stream; the mic stream is for the "me" speaker label. Consider echo handling if mic text duplicates interviewer text.

### T10 — Anthropic streaming AnswerEngine (tested against a stubbed URLProtocol; never called the real API)
- `AnthropicAnswerEngine` (Core): POST `/v1/messages`, headers `x-api-key`, `anthropic-version: 2023-06-01`, body `{model,max_tokens(700),stream:true,system,messages}`; reads SSE via `URLSession.bytes(for:).lines`. `AnthropicStreamParser` handles `data:` lines only (text_delta → token; message_stop/[DONE] → done; `error` event → throws; ping/start/thinking deltas ignored). Cancelling the consumer cancels the HTTP task (used by T11 when a new question arrives).
- `ProviderError` (shared): `unauthorized` (401/403), `http(status,message)` with the provider's message, `api`, `connectionFailed`.
- Default model comes from `AppSettings.defaultModel` (`claude-sonnet-5-5`). Not validated against the live API.

### T9 — Deepgram streaming Transcriber (tested against a fake socket; never connected to the real service)
- `WebSocketConnection`/`WebSocketConnector` protocols with a `URLSessionWebSocketTask` implementation. Handshake failures (e.g. 401) only surface on first `receive()`, so the session reads `failureStatusCode`.
- `DeepgramTranscriber`: URL params model `nova-3`, `language=multi`, linear16 / 16000 / mono, interim results, punctuate, smart_format, endpointing 300 ms; `Authorization: Token <key>`. One socket per `transcribe` call; reconnect with backoff `[0.5,1,2,4,8]` s, budget resets after any message; 401/403 is fatal (no retry); KeepAlive every 5 s; on audio end sends `CloseStream`, waits up to 2 s for final results, then closes; consumer cancellation closes the socket. Timestamps stay monotonic across reconnects (offset = max end seen).
- Audio is pumped only after the first connection exists (early audio waits in the source buffer). Audio produced during a reconnect gap is dropped.
- Tests: 21 for T9+T10, run 6× with no flakes.

**Unverified against the live services:** `language=multi` accepting Russian on Nova-3 streaming; exact current Deepgram param names; Anthropic model id acceptance. First real call may need small tweaks.

### T11 — SessionController + wiring (pipeline logic fully unit-tested; never run end to end with real audio/keys)
- `SessionController` (Core actor): system audio (interviewer, **essential**) + microphone (**best-effort**) → one `Transcriber` per speaker → `QuestionDetector` → `AnswerEngine`. Emits `SessionEvent`s (`stateChanged`, `transcript` incl. interim, `question(id)`, `answerDelta/Finished/Failed(id)`, `warning`) on one `AsyncStream`. States: idle → starting → running → stopping → idle, or failed(message).
  - A new question cancels the in-flight answer; stale deltas are dropped by id. LLM failure is reported per answer and does **not** end the session.
  - Essential failures (system audio won't start, interviewer transcription fails e.g. unauthorized key, `sourceStopped(.interviewer)`) → `failed` and everything is torn down. Mic failures → `warning` only.
  - History: consecutive finals of one speaker merge into one `Turn` (cap 20). The trailing interviewer turn (the question itself) is excluded from prompt history so the question appears once.
  - Silence rule: detector gets `flush(now:)` every 200 ms using `lastInterviewerEnd + wall time since that segment arrived`, bridging Deepgram's audio-clock timestamps to wall time. Slightly conservative (adds the STT delivery latency) and only matters for questions without a "?".
- App: `SessionCoordinator` (@MainActor, ObservableObject) builds the real pipeline at each start from Keychain keys + `AppSettings` (model, prompt builder), turns events into published UI state (`state`, `lines` with interim replacement, `question`, `answer`, `answerError`, `isAnswering`, `warnings`) for the T12 overlay, auto-stops on system sleep and restarts 2 s after wake, shows setup if incomplete. `GlobalHotKey` (Carbon, ⌃⌥Space toggles the session; reports if the shortcut is taken). Menu has a status line (Idle / Listening / Failed: … / latest warning), Start/Stop item, setup, debug items; menu-bar title shows IH / IH ● / IH … / IH !.
- Tests: 15 for the controller with fakes (spy audio sources, hand-driven transcriber, scripted/hanging engine, controllable clock, event log); stable over 5 runs. Two independent streams (interviewer/me) have no cross-stream ordering guarantee; tests sequence pushes explicitly, and the product treats arrival order as truth.
- **Not yet visible:** no overlay, so transcript/question/answer are only in `SessionCoordinator` state until T12. The only live feedback is the menu status line.
- **Not verified:** hotkey registration/triggering, sleep/wake restart, real end-to-end session (needs Screen Recording + mic grants and both API keys).

### Build gotcha (fixed)
- The Xcode app target shared the name `InterviewHelper` with an auto-generated SwiftPM scheme, so `-scheme InterviewHelper` could silently resolve to the package scheme and build only `InterviewCore` while still printing BUILD SUCCEEDED (stale binary). The app target is now **`InterviewHelper-macOS`** (product name still `InterviewHelper`, bundle id unchanged). Always build with `-scheme InterviewHelper-macOS` and check the binary's mtime / "Target dependency graph (3 targets)".
- Build: `xcodegen generate && xcodebuild -project InterviewHelper.xcodeproj -scheme InterviewHelper-macOS -configuration Debug -derivedDataPath .build/xcode build`

### Second live run — end-to-end result and the 503 fix
- **Verified live (user's screenshot):** system audio (`say -v Milena …` through the speakers) → ScreenCaptureKit capture → Deepgram (Russian, exact text) → question detection → request accepted by Gemini (key valid). The answer then failed with **HTTP 503 "This model is currently experiencing high demand"** from `gemini-flash-latest` (a transient free-tier overload). So the whole pipeline up to the LLM works; answer text/quality and time-to-first-token are still unverified.
- **Fix:** `FallbackAnswerEngine` — tries the primary twice, then backup models (`AnswerProvider.fallbackModels`: Gemini → `gemini-2.5-flash`, `gemini-2.5-flash-lite`; Groq → `llama-3.1-8b-instant`), pausing 0.6 s between attempts. Retries only before the first token (no duplicated/contradicting text), only for 404/408/429/5xx, API errors and network errors; a rejected key (401/403) and bad requests (400) are reported at once. Cancelling the consumer stops further attempts. `AnswerEngineFactory` wraps providers that have backups. Manual retry also works: ⌃⌥↩ re-answers the last question.
- Backup model names are unverified (a wrong name → 404 → next backup, so harmless). Tests: 117 total, stable over repeated runs.

### Third live run — retired Gemini models; honest failure reports
- **Finding (user's screenshot):** every attempt failed and the overlay showed only the *last* backup's error: Google's **HTTP 404 "gemini-2.5-flash-lite is no longer available to new users … use gemini-3.5-flash-lite"**. The 2.5 backups I had chosen from memory were already retired for new accounts; the primary `gemini-flash-latest` had earlier returned 503 (demand spike).
- **Fix 1 (models):** web check (Google AI docs, Nov 2026): current IDs are `gemini-3.5-flash-lite` (retires ≥ Jul 2027), `gemini-3.6-flash` (retires Jan 2027), newer Flash exists. New Gemini defaults: primary `gemini-3.5-flash-lite`, backups `gemini-3.6-flash`, `gemini-flash-latest`. Free-tier eligibility per model is not stated in the docs and has not been confirmed with a real key. Lesson recorded: model IDs rot quickly; never hard-code them from memory — keep them editable and keep backups.
- **Fix 2 (diagnostics):** `FallbackAnswerEngine` now takes model names and, when everything fails, throws `ProviderError.allModelsFailed` listing one line per model with its own reason ("model → HTTP 404: …"), so the overlay shows *why each* failed instead of only the last error.
- **Fix 3 (robustness):** `AnswerEngineFactory` orders attempts: chosen model (retried once) → provider default (when the user picked another model) → provider backups. A mistyped model name now falls back to the default instead of failing outright; Ollama/OpenRouter get the same treatment.
- Tests: 119 total, stable over repeated runs.

## Tech debt / notes
- Screen Recording status can't distinguish denied from not-asked on macOS; UI treats it as "not granted".
- Launch smoke test only (process stayed up 4 s, no crash report); UI not visually inspected — accessibility scripting is not permitted for osascript here. Do a manual look at the Setup/Settings window.
- Model name is a free-text field; no validation.
- Resume is pasted text only (no file import yet).
- `SystemAudioCapture` captures the first display only; app-specific filtering (e.g. just the call app) is a possible later refinement.
- Mic and system streams are independent: if the mic picks up speakers (no headphones) the same words may appear under both speakers; not handled.
- Audio produced during a Deepgram reconnect gap is dropped (documented in T9).
- QuestionDetector cue list is a heuristic; tune with real transcripts in T13.
- `flush(now:)` expects the caller (SessionController, T11) to tick it ~every 200 ms.
- Detector keeps only the latest utterance; history of turns is the caller's job (SessionController).
